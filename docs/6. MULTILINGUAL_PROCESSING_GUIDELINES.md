# Multilingual Processing Guidelines

## 📋 Purpose

Handle **Sinhala**, **Tamil**, and **English** reliably in the OpenJustice legal assistance platform. Ensure accurate language detection, correct prompt selection, and language-aware processing throughout the pipeline.

---

## 🎯 Core Principles

1. **Auto-Detection** — `LanguageDetectionService` identifies language via Unicode analysis
2. **Native Prompts** — Separate system prompts per language (not translations)
3. **Fallback to English** — Default when detection fails or language is unsupported
4. **Unicode-First** — Detection based on character ranges, not external libraries

---

## 🌍 Supported Languages

| Language | Code | Script  | Unicode Range   | Detection Threshold |
|----------|------|---------|-----------------|---------------------|
| English  | `en` | Latin   | `a-zA-Z`        | > 50% of characters |
| Sinhala  | `si` | Sinhala | `U+0D80–U+0DFF` | > 30% of characters |
| Tamil    | `ta` | Tamil   | `U+0B80–U+0BFF` | > 30% of characters |

## 🔍 Language Detection

The `LanguageDetectionService` determines the user's language by analyzing the Unicode character distribution in the input text. It counts characters from each script's Unicode block and uses percentage thresholds to determine dominance.

### Implementation

```python
# app/application/services/language_detection_service.py
import re
from typing import Optional

class LanguageDetectionService:
    """Detect language of user input through native Unicode bounds."""

    SUPPORTED_LANGUAGES = {
        'en': 'English',
        'si': 'Sinhala',
        'ta': 'Tamil'
    }

    DEFAULT_LANGUAGE = 'English'

    @classmethod
    def detect_language(cls, text: str) -> str:
        """Determines the primary language based on Unicode block prevalence."""
        if not text or len(text.strip()) < 2:
            return cls.DEFAULT_LANGUAGE

        try:
            language_code = cls._detect_by_unicode(text)
            if language_code:
                detected = cls.SUPPORTED_LANGUAGES.get(language_code, cls.DEFAULT_LANGUAGE)
                logger.info(f"Detected language context: {detected} (code: {language_code})")
                return detected
            return cls.DEFAULT_LANGUAGE
        except Exception as e:
            logger.error(f"Language detection malfunction: {e}")
            return cls.DEFAULT_LANGUAGE

    @staticmethod
    def _detect_by_unicode(text: str) -> Optional[str]:
        """Map string boundaries determining structural dominance of language."""
        # Sinhala: U+0D80–U+0DFF
        sinhala_chars = len(re.findall(r'[\u0D80-\u0DFF]', text))
        # Tamil: U+0B80–U+0BFF
        tamil_chars = len(re.findall(r'[\u0B80-\u0BFF]', text))
        # Latin/English: a-zA-Z
        latin_chars = len(re.findall(r'[a-zA-Z]', text))

        total_chars = sinhala_chars + tamil_chars + latin_chars
        if total_chars == 0:
            return None

        sinhala_pct = sinhala_chars / total_chars
        tamil_pct = tamil_chars / total_chars
        latin_pct = latin_chars / total_chars

        # Determine threshold dominance
        if sinhala_pct > 0.3:
            return 'si'
        elif tamil_pct > 0.3:
            return 'ta'
        elif latin_pct > 0.5:
            return 'en'
        return None
```

### Design Rationale

The service uses **Unicode character ranges** rather than external libraries like `langdetect` or `fastText`. This approach is:

- **Zero-dependency** — No additional packages to install
- **Deterministic** — Same input always produces the same result
- **Fast** — Simple regex counting, no model loading
- **Reliable for target scripts** — Sinhala and Tamil have distinct, non-overlapping Unicode blocks

The lower threshold (30%) for Sinhala/Tamil accounts for mixed-script input (e.g., Singlish text with Latin letters mixed with Sinhala characters).

## 🌐 Integration with LLMService

Language detection is called inside `LLMService._build_messages()` — the central point where all prompts are assembled before calling the LLM:

```python
# app/application/services/llm_service.py (simplified)
async def _build_messages(self, conversation_id, user_id, query, context):
    # 1. Security check and sanitize
    is_safe, violations = PromptSecurityValidator.is_safe(query)
    safe_query = PromptSecurityValidator.sanitize(query)

    # 2. Detect language from sanitized query
    detected_lang = LanguageDetectionService.detect_language(safe_query)

    # 3. Fetch language-specific system prompt from PromptRegistry
    system_prompt = MultilingualPromptBuilder.build_system_prompt(detected_lang, context)

    # 4. Build message array
    messages = [{"role": "system", "content": system_prompt}]
    # ... add conversation history and user query
    return messages
```

The flow is:

```
User query → PromptSecurityValidator.sanitize()
           → LanguageDetectionService.detect_language()
           → MultilingualPromptBuilder.build_system_prompt()
           → Language-specific PromptRegistry template
           → OpenAI LLM call
```

## 📝 Language-Specific Prompt Templates

Each supported language has a dedicated system prompt registered in `PromptRegistry`. Templates are written natively in each language (not translated from English) to ensure correct legal terminology and natural phrasing.

### Template Registration

```python
# app/application/prompts/multilingual.py
from app.application.prompts import PromptRegistry

# Register language-native templates
PromptRegistry.register("legal_assistant_english", "v1", LEGAL_ASSISTANT_EN_V1)
PromptRegistry.register("legal_assistant_sinhala", "v1", LEGAL_ASSISTANT_SI_V1)
PromptRegistry.register("legal_assistant_tamil", "v1", LEGAL_ASSISTANT_TA_V1)
```

### MultilingualPromptBuilder

The builder maps language codes to template names and formats with the retrieval context:

```python
class MultilingualPromptBuilder:
    """Build language-specific system prompts securely."""

    LANGUAGE_MAP = {
        "en": "legal_assistant_english",
        "si": "legal_assistant_sinhala",
        "ta": "legal_assistant_tamil",
    }

    @classmethod
    def build_system_prompt(cls, language_code: str, context: str) -> str:
        """Fetch and build the correct prompt version."""
        # Fallback to English if unknown language code
        template_name = cls.LANGUAGE_MAP.get(language_code, "legal_assistant_english")
        template = PromptRegistry.get(template_name, "latest")
        return template.format(context=context)
```

### Template Structure

All three templates share the same structure but are written in their native scripts:

1. **Role definition** — Identifies as OpenJustice legal assistant
2. **Mandatory rules** — Only Sri Lankan law, cite sources, admit uncertainty
3. **Transliteration handling** — Parse Singlish natively
4. **Citation format** — `[Source: Act Name, Section Number]` (consistent across all languages)
5. **Clarification rule** — Ask for clarification if input is unclear
6. **Context placeholder** — `{context}` filled with retrieved documents

## 🔀 Fallback Behavior

The system uses a simple, predictable fallback chain:

| Scenario | Behavior |
|---|---|
| Text too short (< 2 chars) | Default to English |
| No dominant script detected | Default to English |
| Unknown language code | `MultilingualPromptBuilder` defaults to English template |
| Detection exception | Caught and defaults to English |

There is no translation pipeline in the current implementation. The LLM receives the query in the user's original language and responds using the language-specific system prompt. The LLM's multilingual capabilities handle response generation natively.

## ⚙️ Language in Document Chunking

When documents are ingested via `RAGService`, a `language` parameter is stored on every `DocumentChunk`:

```python
# app/application/services/rag_service.py
chunk = DocumentChunk(
    document_id=document_id,
    content=split.page_content,
    language=language,       # "English", "Sinhala", or "Tamil"
    embedding=vector,
    ...
)
```

The `DocumentChunk` model stores language as a `String(20)` column with a database index (`idx_doc_chunks_lang`), enabling language-filtered retrieval in the future.

## 📋 Checklist: Multilingual Processing

✅ **Detection**

- [ ] `LanguageDetectionService.detect_language()` called before prompt construction
- [ ] Unicode-based detection for Sinhala (U+0D80–0DFF) and Tamil (U+0B80–0BFF)
- [ ] Fallback to `"English"` on detection failure
- [ ] Detection result logged

✅ **Prompt Selection**

- [ ] `MultilingualPromptBuilder` maps language code to template name
- [ ] Templates registered in `PromptRegistry` with version
- [ ] All three language templates written natively (not translated)
- [ ] Citation format consistent across languages

✅ **Integration**

- [ ] Language detection happens inside `LLMService._build_messages()`
- [ ] Runs after `PromptSecurityValidator.sanitize()` (detect on clean input)
- [ ] Runs before `MultilingualPromptBuilder.build_system_prompt()`

## 🚨 Common Mistakes to Avoid

❌ **Using external detection libraries**

```python
# BAD — project uses built-in Unicode detection, not langdetect
from langdetect import detect
```

❌ **Translating prompts from English**

```python
# BAD — write native templates for each language
SINHALA_PROMPT = translate(ENGLISH_PROMPT, target="si")
```

❌ **Mixing languages in templates**

```python
# BAD — each template must be fully in one language
SINHALA_PROMPT = "You are a legal assistant. සියලු උපදෙස් ඉතා වැදගත්..."
```

❌ **Skipping detection**

```python
# BAD — always detect language before building prompts
system_prompt = MultilingualPromptBuilder.build_system_prompt("en", context)
```
