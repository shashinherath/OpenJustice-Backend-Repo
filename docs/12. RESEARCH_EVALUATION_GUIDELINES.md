# 12️⃣ Research & Evaluation Coding Guidelines

## 📋 Purpose

The OpenJustice platform serves both as a production legal-aid service and an academic research platform. To make the system **academically defensible**, we must ensure that all AI operations, RAG pipelines, and model interactions are rigorous, reproducible, and highly measurable.

---

## 🎯 Core Principles

1. **Academic Defensibility** - All system metrics must be peer-review ready.
2. **Strict Reproducibility** - Experiments must yield identical results given identical inputs and states.
3. **Transparent Evaluation** - Automated evaluations (RAGAS, BLEU/ROUGE) must run in isolated pipelines.
4. **Data Provenance** - Version control all datasets, embeddings, and chunking configurations.

---

## 🧪 Experiment Modes

The system operates under different environment configurations. Code should respect these boundaries to prevent polluting research datasets with demo data.

### 1. Research Mode (`APP_ENV=research`)
Used for formal evaluation and data gathering.
* **Strict Seed Enforcement**: All LLM calls and Random Number Generators (RNG) must use fixed seeds (e.g., `seed=42`).
* **Verbose Telemetry**: Every intermediate step (retrieval scores, chunk IDs, latency) is logged.
* **Immutable Knowledge Base**: The Vector DB cannot be updated during a research run to prevent data drift.

### 2. Demo/Production Mode (`APP_ENV=production` / `demo`)
Used for real-world user interaction.
* **Dynamic Responses**: LLM temperature is non-zero (e.g., `0.2`) to provide conversational naturalness.
* **Performance Focused**: Minimal logging to prioritize speed.
* **Live Knowledge Base**: Documents can be continuously ingested and updated.

```python
# app/config.py
class Settings(BaseSettings):
    APP_ENV: str = "demo" # 'demo', 'research', 'production'
    EVALUATION_SEED: int = 42

    @property
    def is_research_mode(self) -> bool:
        return self.APP_ENV == "research"
```

## 📊 Metric Collection Rules

Metrics must be systematically captured at every layer of the AI pipeline.

### Required Metrics per Request
1. **Retrieval Metrics**:
   * `top_k_requested`: Number of chunks requested.
   * `top_k_returned`: Number of chunks actually returned.
   * `cosine_similarities`: Array of scores for the retrieved chunks.
   * `retrieval_latency_ms`: Time taken to fetch chunks.
2. **Generation Metrics**:
   * `input_tokens`: Prompt + Context token count.
   * `output_tokens`: Generated answer token count.
   * `generation_latency_ms`: Time taken by the LLM.
   * `model_version`: Exact model string (e.g., `gpt-4o-2024-05-13`).

### Logging Format
Always log evaluation metrics as structured JSON for easy export to pandas/Jupyter Notebooks.

```python
# app/core/evaluation_logger.py
import json
import logging

eval_logger = logging.getLogger("evaluation")

def log_evaluation_metric(query_id: str, metric_type: str, payload: dict):
    """Log structured metrics for academic analysis."""
    if settings.is_research_mode:
        log_entry = {
            "query_id": query_id,
            "metric_type": metric_type,
            "payload": payload,
            "timestamp": datetime.utcnow().isoformat()
        }
        eval_logger.info(json.dumps(log_entry))
```

## 🤖 RAGAS Integration Standards

We utilize **RAGAS (Retrieval Augmented Generation Assessment)** for automated, reference-free evaluation of the RAG pipeline. 

### Core Metrics to Evaluate
1. **Faithfulness**: Does the answer hallucinate, or is it strictly derived from the retrieved context?
2. **Answer Relevance**: Does the answer directly address the user's question?
3. **Context Precision**: Are the most relevant chunks ranked at the top?
4. **Context Recall**: Did the retriever fetch all the necessary information to answer the question?

### Pipeline Execution
RAGAS evaluations should run asynchronously in a dedicated evaluation pipeline, **not** during the user's synchronous request loop.

```python
# scripts/evaluate_ragas.py
from ragas import evaluate
from ragas.metrics import faithfulness, answer_relevance, context_precision

def run_ragas_evaluation(eval_dataset):
    """Run RAGAS metrics against a static evaluation dataset."""
    metrics = [faithfulness, answer_relevance, context_precision]
    
    result = evaluate(
        dataset=eval_dataset,
        metrics=metrics,
        llm=evaluation_llm  # Use a deterministic, high-capacity model as the judge
    )
    return result.to_pandas()
```

## 📝 BLEU / ROUGE Usage

While RAGAS is used for semantic assessment, lexical metrics like BLEU and ROUGE are used strictly for **Translation** and **Summarization** tasks.

### Translation Evaluation (Sinhala / Tamil ↔ English)
* **BLEU (Bilingual Evaluation Understudy)**: Primary metric for evaluating translation precision. 
* **Rule**: Always use `sacrebleu` to ensure standardized tokenization across languages, particularly for Sinhala and Tamil.

### Summarization Evaluation
* **ROUGE (Recall-Oriented Understudy for Gisting Evaluation)**: Primary metric for evaluating legal document summarization.
* **Rule**: Track `ROUGE-1`, `ROUGE-2`, and `ROUGE-L`.

```python
# app/evaluation/lexical_metrics.py
from evaluate import load

bleu_metric = load("sacrebleu")
rouge_metric = load("rouge")

def evaluate_translation(predictions: list[str], references: list[list[str]], language: str):
    """Evaluate translations using SacreBLEU with language-specific tokenization."""
    # Note: Use appropriate tokenizers for si/ta if supported, otherwise fall back to character/word level.
    results = bleu_metric.compute(predictions=predictions, references=references)
    return results['score']
```

## 🗃️ Dataset Versioning

To make experiments defensible, the underlying data must be immutable and versioned.

### Vector Database Versioning
* All chunks in the `document_chunks` table must carry an `embedding_version` and `chunking_version` (e.g., `v1`).
* If the embedding model or text splitter logic changes, increment the version (e.g., `v2`). **Do not overwrite `v1` vectors** until the research cycle is complete.

### Evaluation Datasets
* Ground-truth datasets (Query + Context + Answer) must be stored in DVC (Data Version Control) or heavily versioned JSON/CSV files.
* Format for Ground Truth:
```json
{
  "dataset_version": "1.0",
  "samples": [
    {
      "query_id": "eval-001",
      "question": "What is the penalty for theft under Sri Lankan law?",
      "ground_truth_answer": "According to Section 367...",
      "ground_truth_context_ids": ["doc_45_chunk_2"]
    }
  ]
}
```

## 🔒 Reproducibility Guarantees

If a researcher runs the system with the same configuration 6 months from now, they must get the same output.

### 1. LLM Determinism
When `APP_ENV=research`:
* Force `temperature=0.0`.
* Pass the `seed` parameter to the OpenAI API.
* Use exact model snapshots (e.g., `gpt-4o-2024-05-13` instead of just `gpt-4o`).

### 2. Retriever Determinism
* HNSW Vector indexes are highly accurate but can exhibit slight non-determinism during index building. For strict evaluation, consider running tests against an Exact Nearest Neighbor (Flat) index if absolute reproducibility is questioned.
* Always enforce a `max_distance` threshold explicitly rather than relying on dynamic shifting thresholds during formal evaluations.

### 3. Execution Environment
* Lock all dependencies in `requirements.txt` or `uv.lock`.
* Document Python version and OS explicitly in research publications based on this architecture.
